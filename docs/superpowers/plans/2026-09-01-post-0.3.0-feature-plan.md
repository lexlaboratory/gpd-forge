## Ordering, and why this order

The rule is **unblock-per-unit-of-risk**, and it produces an order that looks backwards until you follow the dependencies:

1. **Truth first, because five downstream features would inherit a lie.** `GET /tdp` with an owner, in-game confirmation, `/metrics`, runtime projections and the manual-mode hold all want to report *what is in force and who put it there*. Today the daemon does not know: `ModeState` holds a string, `TdpVerified` is a literal, the audit log records no actor, and the readback parser turns "no answer" into `0`. Build any of those on today's foundation and the most confident number in the API is the most wrong one. This phase has zero hardware writes and unblocks the most.
2. **Evidence second, because the project's own biggest open item is arithmetic.** The ROADMAP admits `gaming-battery`'s frames-per-watt claim is "arithmetic, not evidence", and the ~9 W overhead — the largest single term in every battery decision here — exists only as prose in `core/Profiles/Modes.cs:68-70`. Measurement is cheap, driverless, and it is the thing that decides whether the mode that shipped in 0.3.0 was real.
3. **Read-only hardware third**, because the vendor WMI plane is the one new hardware surface that involves no register guessing and no new binary — and its first milestone reads nothing it cannot cross-check against a value this daemon already reads correctly.
4. **Reversible OS writes fourth.** Windows power policy is a genuine lever RyzenAdj cannot reach, costs no driver, and the worst outcome is a slow machine — but it silently mutates a scheme the user also owns, so it must not ship before the restore discipline of phase 1 exists.
5. **The session host last**, because it is the least urgent and the most structural: it unblocks three future features and delivers one.

# Phase H1 — Provenance, and four live defects

**No hardware writes. No new dependency. This is the phase that makes every later number sayable.**

### 1. Who set the watts

An `owner` on every TDP write, threaded to the audit log and to a new `GET /tdp`. There are **eight** writers today and none is recorded: `ForgeWorker.cs` at the guardian throttle, the charge-guard ceiling, the throttle-clear restore, the tuner sweep and auto-FPS; plus `POST /mode`, `POST /tdp` and `POST /panic`. Owner belongs on `ModeState`/a new `TdpState`, not on a worker, because two workers write it.

`GET /tdp` returns `{ stapmW, owner, verified, backend, readAtUtc }` where:
- `verified` is **nullable**. `TdpVerified: true` stops being a literal; `RyzenAdjOutput.Parse`'s `?? 0` becomes `null`; with the gate closed `StubTdpBackend` echoes the request, so `backend: "stub"` must be visible or the endpoint is a liar with a timestamp.

### 2. The anti-standby leak

`POST /jobs` on AC takes an `AntiStandbyService` hold that nothing releases — one request pins Windows awake for the service's uptime, `GET /ai` reports a holder count that never drops, and **it silently defeats Standby Doctor, which is this project's flagship subsystem.** Fix: stop acquiring until something can release. Do not build a job executor (see *Not doing*).

### 3. The dedupe key that prevents coalescing

`ForgeWorker.cs:89` builds `$"guardian:{g.Severity}:{g.Alert}"` and `GuardianEvaluator` embeds the reading in `g.Alert`, so one degree of change opens a new alert. The correct shape is already written one screen below for the charge guard: *"One dedupe key for the whole feature, not one per hour count."* Key on `guardian:thermal-throttle` / `guardian:battery-low`.

### 4. The lists that drifted, and the docs that lie

- Extend `ModeCatalogueTests` to parse `mcp/server.mjs`, `scripts/forge-hotkeys.ps1`, `ui/src/CommandPalette.tsx` and `ui/src/pages/ProfilesPage.tsx` — same `ReadRepoFile` + regex shape, same loud "the parser stopped matching" assertion. Fix the four copies it then fails on. `mcp/server.mjs` also tells agents "PresentMon not yet integrated", which has been false since `GPDFORGE_ENABLE_FPS` was wired.
- ~~`docs/api.md:9` promises "Auth: bearer token" that does not exist. `docs/api.md:497` documents `GET /jobs/:id → { log: string[] }` with no such route. `docs/api.md:166` still lists four modes.~~ **Done 2026-09-02, and it was worse than this line says:** besides the ghost route, the job record was documented with three fields that have never existed, two statuses nothing produces, and a scheduler — `cmd` is stored and never executed. `GET /audit` was serving the complete hardware-write history with no section at all. The mode union in this document had drifted to five while prose ninety lines below listed six. All now checked by `ApiDocRoutesTests` and a fifth `ModeCatalogueTests` surface, because correcting the prose by hand is what was done last time and it drifted anyway. Delete the claims or build them — a doc asserting a mechanism that is absent is the project's own cardinal sin.
- Replace `AllowAnyOrigin` with a two-entry allowlist (`http://tauri.localhost`, `http://localhost:5188`). The web UI and overlay are same-origin and need no entry. Today any page the user visits can `POST /tdp`, `POST /panic` and read `GET /audit`.
- ~~`FanCurve.Interpolate` gets sorting and duplicate-temp rejection **at the store boundary**~~ — **done 2026-09-02, but not as written: there is no store boundary.** `CurvePoint` is constructed nowhere outside `FanCurve.cs`, and `POST /fan` takes a mode and a duty, never a curve, so no user-authored curve can reach `Interpolate` today. Fixed with a test over the three shipped curves plus one that pins that failure — not with a sort inside a function that runs every worker tick to defend against an input that cannot vary at runtime.

### What H1 does NOT do

No auth token (see *Decisions*). No job executor. No webhook. No change to what any hardware path writes.

# Phase H2 — Evidence: make this project's own claims checkable

**No hardware writes. This phase exists because the ROADMAP contains two admissions of arithmetic and this is what retires them.**

### 1. Mode and energy on the session row

`SessionTick` carries no mode (`core/Sessions/SessionModels.cs:16-24`), and the mode **changes mid-session by design** — `ForgeWorker.cs:76` flips it on the AC/battery edge and focus rules switch it too. So capture mode **per tick** and store a dominant mode *plus the fraction of ticks in it*; **exclude mixed sessions from any comparison rather than averaging them.**

Replace the integer-percent battery delta with **start/end `RemainingCapacity` in mWh** — already read in mWh by `BatteryEstimator.cs:88`. This is not a refinement: I read the live store, and every one of the 34 on-battery sessions has a `BatteryUsedPct` of 1, 2 or 3 with a median duration of 120 s. A 1-point drop over 118 s is ±100 % on the derived rate. **Any "1 h 34 min left" derived from that is fabricated precision.**

### 2. The two battery fields already on the wire

Add `ChargeRate` and `Voltage` to the `BatteryStatus` query the daemon already runs twice. This is one extra column, and `ChargeRate` is named as an input to the charge guard in the project's own plan while `ChargeGuardService.Observe` has no such field. Land the dead ends beside `BatteryHealth.cs:12`: cycle count 0, `BatteryRuntime` 0xFFFFFFFF, no UCSI/UCM device.

⚠️ "Voltage sag under load" is **derived across two samples**. It gets the `StandbyDrain` treatment — measured across an observed interval or `null`. Never a per-tick number labelled sag.

### 3. Platform overhead, measured instead of asserted

The ~9 W lives only in a comment. Replace it with a persisted on-battery least-squares accumulator (running sums in `DataRoot`, **not** a fit over the 1-hour in-memory ring, which loses everything on restart), fed **60 s block means of both channels** — `DischargeRate` is a coarse slow pack counter and `PackageW` is instantaneous RAPL, and fitting a fast x against a slow y attenuates the slope and *inflates* the intercept. Publish intercept, slope, n, x-range and residual, `null` until it qualifies.

Then `BatteryEstimator.Project` may use the measured intercept — and only then. `GET /battery/budget` also needs its existing `int[]? tdpWatts` parameter plumbed through as a query so the overlay can project at the stepper's value.

### 4. Two exports, one grouping

`GET /sessions/export.csv` (precedent: `CsvExport.cs`). Alert recurrence grouped by key and day over the 30-day retention — only meaningful once H1 fixes the key.

### The gate — one number, measured or refused

**The `gaming-battery` A/B runs, or the tool says which precondition failed.** Two equal-length runs of one real game, `/sessions` reporting fps average, 1 % low, mWh consumed, and dominant-mode fraction ≥ 0.95 on both. If the runs come back mixed-mode, the feature must **exclude them and say so** — observe that refusal deliberately by switching modes mid-run once.

**And the fit must be rejectable.** The fitted intercept has to land in a stated band around the Phase-D bench point (packageW 6.2 / dischargeW 16.2). If it does not, the overhead figure stays `null` and `Project` keeps its current honest roughness. Feed the accumulator a synthetic slow-y/fast-x pair offline and observe the inflated intercept before trusting the real one.

### What H2 does NOT do

No per-game regression detection and no per-game runtime estimate: the live store contains **zero games** — the top apps are `Orca.exe`, `msedgewebview2.exe` and `rustdesk.exe` — so the first output of either feature is a trend report about a browser. Revisit when the store has games. No hibernate saving estimate: `SleepStudySession.DrainIsMeaningful` deliberately excludes S4 because a hibernating machine's exit reading is *absent, not zero*, and any saving figure would rest on an assumed 0 W.

# Phase H3 — The vendor WMI-ACPI plane, read-only

**First hardware phase. Firmware-declared, named, typed methods — no register guessing, no new binary, no WinRing0.**

Three milestones, and the phase ends after milestone 2 unless a decision is taken.

**M1 — `--probe-wmi-acpi`, output only.** In the style of the existing `--probe-*` commands, behind `GPDFORGE_ENABLE_HARDWARE`. Calls `GetHwTemp`, `GetFanControl`, `GetPowerMode`, `GetKbdBltBrightness` as SYSTEM. Prints what it saw, including "the call failed" — nothing in this tree has ever *invoked* one of these methods, only enumerated them.

**M2 — cross-check.** Read `GetFanControl` and `PawnIoFanRpm`/`EcRam` duty in the same second and compare. `GpdFanController.SetManualDuty` already read-back-verifies, so there is a known-good value to check against. **If the two disagree, the phase stops and the disagreement is the deliverable.**

**M3 — writes: gated on a decision (see *Decisions*).** `GpdFanController`/`PawnIoEcPort` already own the fan duty register. Two owners of one register is precisely the failure the double gate exists to prevent.

**Gate and restore path for anything in M3**: unchanged double gate (`GPDFORGE_ENABLE_HARDWARE` **and** `GPDFORGE_ENABLE_FAN_CONTROL`), probe-with-auto-restore, and `FanControlPolicy.IsUsableTemperature`'s fail-safe to firmware AUTOMATIC. `ResumeRestoreWorker` hands the EC back to AUTOMATIC after a suspend; any new owner must be in that path or it is not restorable.

### The gate

- **Observe the refusal.** Run the probe with `GPDFORGE_ENABLE_HARDWARE` unset and observe it declines by name. Run it unelevated and observe the access denial rather than a silent empty result.
- **Observe the temperature move.** `GetHwTemp` under a deliberate sustained load must track the existing thermal-zone/LHM reading within a stated band across ≥ 3 minutes. A value that does not move is not a temperature.
- **Observe the duty agree.** M2's paired read must match within one quantisation step, logged with both raw values, on ≥ 20 consecutive samples spanning at least one fan-curve step change.

### What H3 does NOT do

**`Get/SetFeatureValue` is carved out of scope entirely** — an undocumented generic channel is register-guessing under another name. **`SuRwECRegInterface.WriteECReg` is out of scope**: its `GroupOffsetValue` packing is undocumented, so it would add a *second* guess on top of the first, and it is unrestricted arbitrary EC access, which inverts ADR-0001's whole reason for PawnIO ("the module declares which addresses it touches"). A read-only `ReadECReg` dump-and-diff instrument stays available as the thing ADR-0004 says becomes worth building *the moment the BIOS-setup check finds something* — and not before. No keyboard-backlight writes until brightness ownership is settled against `DisplayService`.

# Phase H4 — Windows processor power policy, per mode

**Reversible OS writes. No driver, no elevation beyond what the service has, and nothing here can damage hardware — the worst outcome is a slow machine.**

Per mode, AC and DC separately: `PERFEPP`, `PERFBOOSTMODE`, `CPMINCORES`/`CPMAXCORES`, autonomous mode. These are orthogonal to STAPM and RyzenAdj cannot reach them: TDP sets the ceiling, EPP and boost decide how violently the part sprints to it, which is what turns a 15 W budget into smooth frames or a sawtooth.

Two implementation facts already paid for in this repo, both mandatory:
- **`PowerSetActiveScheme` after every write.** `HibernatePolicy.cs:143-145`: "editing the scheme without re-activating it leaves a setting that reads as changed and behaves as it was."
- **Read and write by GUID through the Win32 power API, never by parsing `powercfg /q`** — that output is localised, and this repo has been bitten by localisation twice (the hibernate parser, and `HidReenumerator` keying on `PNPDeviceID`).

🔴 **The per-efficiency-class frequency cap does not ship as originally described, and the reason is load-bearing.** `PROCFREQMAX1` is "maximum frequency for efficiency class 1", and on this device `GetLogicalProcessorInformationEx` reports the **first 4 cores at class 1** — the Zen5 *performance* cores, not the Zen5c ones. The proposal to "cap the little cores in `gaming-battery`" would have capped the big ones, silently, with nothing on screen saying why. Either drop the cap, or derive the class at runtime and label it **by measured class**, never by an assumed core name.

**Gate and restore path**: snapshot every index touched before writing, restore on mode exit *and* on service stop, and never write to a scheme the daemon did not create. These writes sit behind the same conflict guard `ProfileApplier` uses (`PowerControllerDetector`) — otherwise a mode switch that correctly yields its TDP to MotionAssistant still lands its power policy.

### The gate

- **Falsify the restore by killing it.** Enter a mode, confirm the indices changed by reading them back, then **`Stop-Service` mid-mode** and observe every index return to its snapshot. Then kill the process ungracefully and observe what happens — if that path cannot restore, say so in the ADR rather than discovering it later.
- **Observe the yield.** Start MotionAssistant, switch modes, and observe **no** power-policy write landed — the same tick that skips the TDP write. A guard enforced on one door is one you walk around through the other.
- **Observe the class.** Log the measured efficiency-class map at startup and assert it against `GetLogicalProcessorInformationEx` in a test. The inverted assumption above must be impossible to reintroduce silently.

### What H4 does NOT do

No Windows 11 power-mode overlay (`PowerSetActiveOverlayScheme` is undocumented — separate item, needs `PowerGetActualOverlayScheme` readback to stay honest). **No core-parking preset ships without measurement on this hybrid part** — deriving values from HandheldCompanion's is inheriting another device's answer, which is the same mistake as inheriting a Linux driver's register table.

# Phase H5 — Split the session host; add the GPU half of telemetry

Today `GpuAgentLoop.cs:37` exits the **whole process** when `GPDFORGE_ENABLE_GPU_PROFILES` is unset. That single line is why three separate future features (gyro-to-mouse, overlay volume, an XInput chord summon) have nowhere to live — anything added to the agent dies with an unrelated opt-in.

1. **Split the session host from the ADLX tenant.** The host runs; the ADLX *feature* is gated, not the process. Same assembly, same ADR-0002 containment, no new binary.
2. **ADLX performance monitoring, in the agent.** Transcribe `IADLXPerformanceMonitoringServices` (slot 9) from the SDK header — it is a **separate vtable with no canary**, and `AdlxSettings.cs:59-64` records exactly what happens when an inherited slot index compiles and returns `ADLX_UNKNOWN_INTERFACE`. Probe `IsSupported` before every read.
3. **Expose under `GET /gpu`, not flattened into `/telemetry`.** These are second-hand values arriving via `POST /gpu/state` with a 30 s freshness stamp. Putting them beside first-hand daemon readings destroys exactly the provenance distinction `GpuAgentState.cs` was written to preserve — and writes blank history columns nobody can distinguish from a measured gap.

### The gate

- **Observe the three distinct states.** With the GPU gate unset, the session host must still be running and `GET /gpu` must say *"GPU features disabled"* — distinct from *"no agent has reported yet"* and from *"the agent says ADLX is unavailable"*. Produce all three deliberately and screenshot each.
- **Observe the canary catch a wrong slot.** Point one metrics call at a deliberately wrong index in a test build and confirm it is refused before being called through, not after.

### What H5 does NOT do

No ADLX FPS — `PresentMonFrameRateProbe` already owns that field and a second source would silently disagree. No Vari-Bright: it is a driver-side auto-dimmer that would fight `DisplayService.SetBrightness` and `NightModeService`'s gamma ramp, and that ownership question is a separate decision. No gyro, no volume — H5 makes them possible and deliberately does not build them.

# Decisions for Alex — not made silently here

1. **BIOS setup charge threshold.** Still the cheapest open item in the project (~10 min, hold `DEL` at boot). ADR-0004 closed the ACPI route; this is the one remaining lead, and it decides whether an EC dump-and-diff instrument is ever worth building.
2. **Who owns fan duty?** H3-M3 does not proceed without an answer. Options: keep PawnIO and use WMI read-only as a cross-check (safest, my recommendation), or migrate to the WMI method and retire the PawnIO write path. Not both.
3. **API auth.** I am proposing the Origin allowlist and **no token**, recorded as an ADR. Every first-party client that mutates state is a non-elevated user-session process (tray, hotkeys, Tauri shell, overlay in Edge). A token ACL'd to SYSTEM breaks all four; a token the user can read is readable by every process that can already reach loopback. On a single-user handheld it buys close to nothing. **If you disagree, say so before H1 lands** — it is much cheaper before the allowlist ships than after.
4. **Overlay topmost over exclusive fullscreen.** Still a decision, not work: require borderless-windowed, or hook the presentation chain and resurrect the dependency this project dropped. Should land as an ADR either way, and any XInput-chord summon must not be described as though it solved this.
5. **The 60 Hz panel and resolution switching.** I am not proposing per-mode resolution changes — a desktop mode change fired automatically by the focus worker under a running game is a different class of disruption from a TDP change, and "revert if unconfirmed" assumes a human is watching, which is precisely the case where nobody is. Say if you want the read-only half (report supported resolutions) anyway.
6. **Two game runs for H2's gate.** The A/B needs your hands on the device. Without it, `gaming-battery` stays arithmetic.

# Not doing, and why — so none of it is re-proposed

- **A job executor that runs `Job.Cmd`.** The daemon is LocalSystem, the API has no auth, and `Cmd` is an arbitrary string. An executor converts `POST /jobs` into unauthenticated arbitrary code execution as SYSTEM. If a runner ever ships it dispatches a **fixed allowlist of named daemon operations**, never a command line.
- **`POST /webhooks`.** Same shape: a mutating registration route on an unauthenticated API in a SYSTEM process, aimed at an arbitrary host, carrying temperatures, battery state and process names. If webhooks happen at all, registration is a config file under `%ProgramData%` where file ACLs do the authorising — and it gets an ADR line, because it is the first time this project sends device telemetry off the box.
- **`GET /metrics` in OpenMetrics.** Deferred, not rejected — but only with null-omission as the *stated contract*: a sensor reading null is omitted entirely, no gauge line, no 0, no NaN. OpenMetrics has no null, and a gauge emitting 0 for an unread sensor re-creates the exact bug 0.3.0 spent a release removing, this time in a time series where nobody will ever see it was fabricated.
- **`IDXGIAdapter3::QueryVideoMemoryInfo` for live VRAM.** It is **per-process**: a daemon calling it reports its own ~0 MB, not the game's. (`GetDesc1`'s 64-bit `DedicatedVideoMemory` is a different call and is worth having — it lifts `VramAdvisor` off its 4095 MiB ceiling. Separate small item.)
- **XInput rumble for critical alerts.** A shared, last-writer-wins write with no readback: any game using rumble overwrites it within a frame, so the channel reserved for critical alerts is unreliable exactly when it matters. A UI that then says "delivered" fabricates a value. The unmeasured premise underneath — whether a tray balloon reaches the user during a fullscreen game at all — is a 10-minute test that nobody has run.
- **A wizard button that arms the overlay hotkey.** There is no path: the daemon is session 0 and cannot register a user-session hotkey, the Tauri shell exposes no command, and the wizard runs in a plain browser. Worse, `overlay-hotkey.ps1 -SelfTest` registers then unregisters, so it **fails when the resident listener is running correctly** — a false negative on the success case. Show the exact `-EnableHotkeys` command instead.
- **A launcher-library scrape for the app-rules pick-list.** `GET /sessions/games` already exists, is already consumed by `SessionsPage.tsx`, and is built from measured evidence. A scrape produces a *worse* list — games never played. (Steam's `appmanifest_*.acf` remains worth importing later, but only if it resolves the **executable**: `AppRulePolicy.Matches` is substring-on-process-name, and `"Cyberpunk 2077"` will never match `Cyberpunk2077.exe`. Playnite is out of reach entirely — per-user LiteDB, and nothing in `core/` resolves the interactive user's profile.)
- **Guessing an EC register.** Stated once here and twice in the pending-features plan, and it holds for the WMI transport too: a firmware method with an undocumented packed argument is the same guess wearing a better coat.
