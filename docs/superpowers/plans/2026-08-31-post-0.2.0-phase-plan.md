# Post-0.2.0 phase plan

**Date**: 2026-08-31
**Baseline**: `f9d5687` on `origin/main`, v0.2.0 published, daemon `a0a999f` running on device
**Method**: audited against the tree and the live daemon before planning, per the standing rule in
this repo — four false checkboxes were found in a single session on 2026-08-30, so the roadmap is
treated as a claim to verify, not a source.

---

## What the audit found

Everything below was measured on 2026-08-31, not read from the roadmap.

### The roadmap contradicts itself, and the contradiction is not cosmetic

`docs/ROADMAP.md` opens Phase 6 with:

> **Phase 6 — The broker** *(unblocks the fan, and is the single biggest blocker in the project)*
> - [ ] **PawnIO integration + audit log**

That work is done. On disk right now:

| Claimed missing | Actually present |
|---|---|
| PawnIO integration | `core/Fan/PawnIoEcPort.cs`, `core/Fan/PawnIoFanRpm.cs` |
| Audit log | `core/Broker/HardwareAuditLog.cs`, `core/Broker/AuditingControllers.cs`, `GET /audit` |
| `Fan/` runtime EC read | daemon reports **3328 rpm** live |
| Hysteresis curves | `core/Fan/FanCurve.cs`, driven every tick from `ForgeWorker` |
| Resume re-init | fixed 2026-08-30; restore reaches the real controller |

Phase 1 already documents all of it as done. So the same work is ticked in one phase and listed as
*the single biggest blocker in the project* in another. Anyone reading the roadmap top-to-bottom —
including a future agent session — concludes the fan is blocked. It is not.

The same duplication runs through two more items:

- **Hibernate helper**: `[x]` in Phase 2, `[ ]` in Phase 8. One item, shipped once, tracked twice.
- **First public OSS release**: `[~]` in Phase 4, `[x]` in Phase 5. v0.2.0 is published.

And two checkboxes cover things that do not exist in any form:

- **RTSS**: zero code. `grep -ril rtss core/ ui/src/` matches one string in `HardwarePage.tsx` and
  three vendored DLLs. It is open in Phase 1 *and* Phase 4.
- **WebSocket + named pipe**: zero code, and `docs/api.md` already records that no client wants a
  stream.

**This is a documentation-governance defect, not a backlog problem.** The roadmap is carrying four
distinct roles at once — rules, map, status, and history — and status is the one that rots fastest.
The `living-docs-governance` practice names exactly this failure: one canonical owner per fact,
everything else links to it.

### The working tree is duplicated, and the stale copy is the one the vault calls canonical

| Tree | HEAD | Age |
|---|---|---|
| `C:\Users\Alex\orca\workspaces\gpd-forge\weakfish` (this one) | `f9d5687` | current |
| `C:\Users\Alex\gpd-forge` | `b26228d` | **40 commits behind**, 2026-08-29 |

The stale tree is clean — no uncommitted work, no stashes, nothing lost. The risk is not data loss,
it is **re-running `install-gpd-forge.ps1` from the old tree**, which would silently reinstall a
build without FRTC, the audit log, the fan restore fix, the hibernate policy or the API startup
tests. The installer would report success. This is the same shape as the 2026-08-28 incident where
the installed binary predated the fix and nothing on screen could say so.

The installed daemon itself is fine: `GET /version` reports commit `a0a999f`, and the only commit
after it (`f9d5687`) touches CI only.

### The sleep study is reporting two hardware events nobody has triaged

`GET /standby` returns, over 116 sessions:

- **Bugcheck `0x133`** on 2026-08-28. That is `DPC_WATCHDOG_VIOLATION` — a driver holding a DPC too
  long. This project loads a Ring0-family driver through LibreHardwareMonitor when hardware access is
  enabled, and talks to the EC through PawnIO. That does not make it ours, but it makes it ours to
  rule out.
- **Failed resume** on 2026-08-29: a 5-hour hibernate whose next event was an abnormal shutdown. The
  roadmap mentions this once, in Phase 4, as a reason a firmware assistant might matter. It is not
  tracked anywhere as an open defect.

Neither appears in any open-fronts list. The sleep study has been shipping this data since it landed
and nothing reads it back.

### Overnight drain still cannot be measured, and the cause is structural

`lastDrainPctPerHour` is `null`. The only sleep blocker is:

```
[PROCESS] \Device\HarddiskVolume3\Users\Alex\AppData\Local\Programs\orca\Orca.exe
```

The agent environment itself is what keeps the machine awake. No amount of code changes this — the
measurement needs a window with the agent shut down. Until then, the drain figure, the
`InferenceHoldWorker` evidence and the hibernate policy's real effect are all unfalsifiable.

### Idle draw is 2.6× package power

Measured on battery, idle: `packageW 6.2`, `dischargeW 16.2`. Ten watts are going somewhere other
than the SoC — panel, backlight, Wi-Fi, USB rails, the fan at 3328 rpm. At 16 W the 45.6 Wh battery
gives under three hours doing nothing. The product's headline promise is battery life, and the
largest single term in that budget is currently unattributed.

### The test suite still cannot fail the way this project actually breaks

Current: **664 `[Fact]`/`[Theory]` across 51 files** (881 cases) and **73 E2E specs** (90 cases).
`ApiStartupTests` closed the "nothing starts a web host" hole on 2026-08-30 — that was the right fix
and it works.

The remaining hole is one layer up: **nothing exercises the packaged Tauri shell.** Every incident
of the last week lived there — the stale bundle with a relative `BASE`, React unmounting on an enum
ordinal, the installer that copied instead of building, the environment key the installer erased.
The E2E suite runs `vite preview` against a mock daemon, which is the one configuration where none
of those can happen.

## The plan

Phases are ordered by what unblocks the most per unit of risk. Each ends at the standing gate:
build → types → lint → tests → security, plus **an effect measured on the device**, never an
installer log.

### Phase A — Make the documentation tell the truth *(no code, unblocks every later phase)*

Nothing here is optional, because every subsequent phase is planned against documents that are
currently wrong.

1. **Split the roadmap's four roles.** Map (what exists, where) stays in `ROADMAP.md`; status
   (what is open, blocked, or intentionally dropped) becomes a short status section with one owner
   per fact; history (why a shape was chosen) moves to ADRs. Applies `living-docs-governance`.
2. **Reconcile the contradictions against the tree**: Phase 6 collapses into Phase 1 with a pointer,
   the duplicate hibernate and release items resolve to their shipped entry, and RTSS and
   WebSocket/named-pipe move to an explicit *dropped, and why* section rather than staying as
   checkboxes nobody can pick up.
3. **Write the three ADRs that already exist as prose** buried in roadmap paragraphs, using
   `architecture-decision-records`:
   - ADR-0001 PawnIO over WinRing0 for EC access (with the Defender/SAC reasoning)
   - ADR-0002 ADLX runs in a user-session agent, and the daemon never holds a handle (with the
     uncatchable `AccessViolationException` consequence)
   - ADR-0003 `/firmware` reports and refuses to flash; `canAttempt` is permanently false
4. **Resolve the duplicate tree.** Either retire `C:\Users\Alex\gpd-forge` or fast-forward it, and
   record which path is canonical where the installer can be run from. Alex's decision — deleting a
   tree is not mine to make.
5. **Fix the README status badge**, which still reads *Phase 1: core working* against a published
   v0.2.0.

**Gate**: every checkbox in the roadmap verified against a file path or a live endpoint. A claim
with no evidence line does not survive the pass.

### Phase B — Close the verification hole that produced every recent defect

Applies `windows-desktop-e2e`, `csharp-testing`, `verification-loop`.

1. **Drive the packaged shell with pywinauto/UIA.** Honest scope limit up front: GPD Forge is Tauri,
   so the content is WebView2 and UIA **cannot** see the DOM — the ECC skill says so explicitly. What
   UIA *can* assert is exactly the layer that has been breaking: the window opens, the title carries
   `daemon=up`, closing hides to tray instead of exiting, the tray menu items exist and respond, and
   the hotkey listeners are resident. The DOM half stays with Playwright.
2. **Run the existing E2E suite against the real daemon at least once per release**, not only the
   mock. The mock has emitted correct data in cases where the daemon did not (the `AlertSeverity`
   ordinal is the proof: `alerts.spec.ts` passed while the app was unmountable on the device).
3. **A contract-parity test between mock and daemon.** Any route whose real response shape diverges
   from the mock fails the build. This is the general form of the bug that took the whole UI down.
4. **Make `verify-install.ps1` assert the effect, not the exit code** — the pattern that caught the
   fan restore lie on 2026-08-30 (`"the EC responded (duty reads 203)"`), applied to every step.

**Gate**: reintroduce the `AlertSeverity` ordinal on a scratch branch and confirm the new tests go
red. A guard nobody has seen fail does not count.

### Phase C — Triage the two hardware events the sleep study is already reporting

Applies `systematic-debugging`, `benchmark-methodology`.

1. **Bugcheck `0x133`.** Pull the minidump if one exists, identify the driver holding the DPC, and
   determine whether GPD Forge's driver surface (LHM Ring0 path, PawnIO) is implicated. If it is not,
   say so with the evidence and close it — an unexplained bugcheck in a power tool's own sleep report
   is a liability whether or not the tool caused it.
2. **The failed hibernate resume.** Correlate with BIOS 0.10 and the hibernate policy shipped in
   Phase 8. This is the concrete case the firmware assistant was written for; it deserves a finding,
   not a mention.
3. **Surface both in the alert centre**, so the sleep study stops being data that only a manual
   `GET /standby` ever reads.

**Gate**: each event ends as either an identified cause or an explicitly ruled-out hypothesis with
the measurement that ruled it out.

### Phase D — Account for the idle watts *(the product's actual promise)*

1. **Attribute the 10 W gap** between package power and pack discharge: panel and backlight at known
   brightness, Wi-Fi/BT, USB rails, fan at 3328 rpm, controller. Measure by subtraction with one
   variable moved at a time.
2. **Feed the result into the battery estimator**, which today models discharge without a term for
   any of it.
3. **Only then consider an idle profile.** A power-saving mode built before the budget is known is a
   guess with a UI.

**Gate**: a documented watt budget that sums to the measured discharge within tolerance. If it does
not sum, the gap is named, not rounded away.

### Phase E — The two hard fronts *(investigation before code)*

1. **HID (Phase 7).** Blocked by a measured fact: all three interfaces report
   `FeatureReportByteLength = 0`, so `HidD_GetFeature` cannot reach the 1024-byte blob. The next step
   is finding how WinControls actually talks to the pad — a config-mode PID, a WinUSB interface, or a
   vendor endpoint. That is USB tracing, not programming. **No write path opens until the transport
   is known.**
2. **Overlay topmost over exclusive fullscreen.** Two honest options, both with costs: require
   borderless-windowed (the user's choice, not ours to force) or hook the presentation chain (which
   is what RTSS exists for, and would resurrect a dependency this project deliberately dropped). This
   needs a decision from Alex before any code, and it should land as an ADR either way.

### Phase F — 0.3.0

Applies `security-review`, `security-scan`, `github-ops`.

1. Security pass over the driver surface, the elevated installer, and the local HTTP API — it binds
   `127.0.0.1` with no auth, which is defensible for a local daemon and should be stated as a
   decision rather than left implicit.
2. Review `mcp/server.mjs` against `mcp-server-patterns`; its write tools reach real hardware.
3. Release through the now-fixed workflow. `scripts/changelog-section.ps1` extracts one section and
   fails loudly when a version has none — that guard has not yet been exercised by a real release.

**Gate**: install from a clean state, verify on device, and confirm the release notes contain one
version's section.

## Sequencing, and why

**A first**, because it is the only phase whose absence corrupts the others: planning Phase 6 work
that shipped a week ago wastes a session, and it has already nearly happened. It is also the cheapest
— no code, no risk, no hardware.

**B second**, because every defect of the past week lived in the gap it closes, and each one reached
Alex's screen before anyone noticed. The suite is large and green and does not cover the failure
mode this project actually has.

**C and D are independent of both** and of each other. C is a liability question; D is the product
question. D is where the user-visible value is, C is where the risk is.

**E is gated on decisions and investigation**, not effort, and should not be scheduled as though it
were coding work.

**F closes the loop** and exercises a release guard that has never run for real.

## Non-goals for this cycle

- No fan write path changes. The double gate and probe-with-auto-restore stay as they are; that
  subsystem was validated physically and does not need attention.
- No new UI surfaces. The HUD redesign is recent and unbroken.
- No BIOS flashing, ever, from this daemon.
